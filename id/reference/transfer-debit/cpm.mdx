## CPM

Customer-Presented-Mode QR (pelanggan menampilkan QR, merchant yang memindai): generate, bayar, query, batal, refund; hasil pembayaran juga datang sebagai notifikasi masuk.

<CodeGroup>
```go example.go
resp, err := transferdebit.CPMPayment(ctx, transport, hb, transferdebit.CPMPaymentRequest{
	PartnerReferenceNo: "2020102900000000000001",
	QRContent: "...",
	MerchantID: "...",
})
if err != nil {
	// errors.Is(err, snap.ErrBadRequest), snap.ErrUnauthorized, etc.
}
```
</CodeGroup>

### `CPMGenerateQR`

CPMGenerateQR memanggil endpoint SNAP Generate QR CPM (Service Code 59, path .../\{version\}/qr/qr-cpm-generate, HTTP POST — tanpa override method). hb harus sudah membawa setiap field yang dibutuhkan snap.HeaderBuilder kecuali Body, yang diisi sendiri oleh CPMGenerateQR agar byte hasil marshal yang persis sama dipakai baik untuk signing maupun body di jalur kirim.

Operasi ini tidak idempotent dan package ini tidak melakukan retry. Caller yang me-retry panggilan yang gagal atau timeout sebaiknya memakai ulang X-EXTERNAL-ID yang sama, karena deteksi duplikat di sisi server berpatokan pada header tersebut.

```go
func CPMGenerateQR(ctx context.Context, t *snap.Transport, hb snap.HeaderBuilder, req CPMGenerateQRRequest) (CPMGenerateQRResponse, error)
```

### `CPM Payment Notification`

<Info>Hanya masuk (inbound) &mdash; package ini tidak memanggil endpoint untuk hal ini. Partner/switcher yang mengirim POST ke callback URL **Anda**; unmarshal body ke `CPMPaymentNotificationRequest` setelah memverifikasinya dengan `snap.ServerVerifier` (lihat [Memverifikasi request masuk](/id/concepts/webhooks)), lalu balas dengan bentuk di bawah.</Info>

**Diterima &mdash; `CPMPaymentNotificationRequest`**

CPMPaymentNotificationRequest adalah body request untuk API Payment Notification (Service Code 79, path .../\{version\}/qr/qr-cpm-notify). Ini adalah callback settlement yang diterima PJP, bukan panggilan yang dibuat package ini — tidak ada fungsi pemanggil yang disediakan, mengikuti konvensi baku package ini untuk endpoint notifikasi masuk (QRMPMPaymentNotificationRequest, Fase 23; DirectDebitPaymentNotificationRequest, Fase 27): caller memasang HTTP handler-nya sendiri untuk path ini, mengautentikasi panggilan masuk dengan ServerVerifier.VerifyTransactionRequest, dan melakukan json.Unmarshal pada body ke tipe ini.

MerchantID dan LatestTransactionStatus bersifat Wajib menurut riset §5.2; setiap field lain Opsional. Riset secara eksplisit mengonfirmasi endpoint ini cocok dengan bentuk dan arah QRMPMPaymentNotification (response hanya-envelope, masuk), berbeda dari klaim "identik secara struktur" pada Cancel Payment (62) yang terbantahkan di bagian yang sama — kutipan ini terbukti benar setelah diverifikasi.

**Request &mdash; `CPMCancelPaymentRequest`**

CPMCancelPaymentRequest adalah body request untuk API Cancel Payment (Service Code 62). OriginalPartnerReferenceNo adalah satu-satunya field Wajib menurut tabel field riset §5.2 sendiri.

Prosa ringkasan riset mengklaim endpoint ini "identik secara struktur dengan QRMPMCancelPaymentRequest/Response" (Fase 24) — klaim itu tidak terbukti: field Wajib QRMPMCancelPaymentRequest adalah MerchantID/Reason (ketiga field originalX di sana juga Opsional), sebuah himpunan yang berbeda dari OriginalPartnerReferenceNo yang Wajib di endpoint ini sendiri. Tabel per-field yang jadi acuan di sini, bukan kalimat ringkasannya — lihat dokumen desain untuk perbandingan lengkapnya. Dimodelkan sebagai tipe independen, tanpa reflection-drift-guard terhadap QRMPMCancelPaymentRequest karena keduanya bukan bentuk yang sama.
